# 3. 문제점의 요약
문제의 현재 상태, 기대 상태, 관련 이해관계자, 제약사항을 정리한다. Discovery의 핵심 맥락을 가장 먼저 이해할 수 있어야 한다.

- 현재 상태
	- **K1 (Mongo 업로드)**: `FlexfabForm.cs` `TryUploadToMongo`는 완성 결과만 올린다(`SaveLogDirect` → `MongoDBUpload=True`일 때, `InsertOne` → `ctsm.product`). FAIL 결과 JSON(`FlexfabForm.Report.cs` `SaveFailJsonSlot`)은 로컬 `Result/{프로젝트}/{날짜}/FAIL/{sn}_{X|Y}_{시각}.json`에만 저장되고 업로드하지 않는다. 재완성 시 이전 결과는 `PASS_DUPLICATE/`로 옮긴다
	- **K2 (품질모니터링)**: 2슬롯 레포 `tools/quality_monitor`의 `etl.py`(`ingest`)·`parser.py`(`load_results`)·`app.py`가 결과 폴더를 `rglob("*.json")`로 **재귀 수집**한다. 하위 폴더를 구분하지 않아 `FAIL/`·`PASS_DUPLICATE/` JSON도 일반 결과처럼 적재된다. 시리얼별 판정(`serial_pass_fail`)은 "측정 행 중 하나라도 OK가 아니면 FAIL" → X단계 FAIL 기록이 있는 보드가 재검 후 완성돼도 FAIL로 집계될 수 있고, 재완성 보드는 중복 집계된다
	- 품질모니터링 코드는 4슬롯 레포 밖(2슬롯 레포 `flexfab_VibeTilt/tools/quality_monitor`)에 있다. 4슬롯은 아직 제조 미배포라 실제 오염은 없음
- 기대 상태
	- K1: FAIL 결과를 DB에 올릴지·어디에 올릴지가 정해져 있고, 양산 DB의 기존 소비자(완성 보드 = PASS 가정)가 깨지지 않는다
	- K2: 품질모니터링이 완성·FAIL·재완성 이력을 **구분해서** 다루고, 수율·SPC 통계가 4슬롯 결과로 왜곡되지 않는다 (FAIL 기록은 오히려 불량 분석에 쓸 수 있으면 좋다)
- 이해관계자
	- 응용기술팀(강병택) — 검사 프로그램·품질모니터링 개발, 결정
	- 제조팀(캔탑스엠) — 성적서·이력 사용, 품질 데이터 소비
	- 품질모니터링(QMP) 운영·사용자 — 수율·SPC 대시보드
	- 양산 DB(MongoDB `ctsm.product`) 소비자 — 품질모니터링 외 소비자는 미확인(OQ-1, K1 결정으로 이번 범위에 영향 없음)
- 제약사항
	- 공용 라이브러리 수정 금지, 결과 JSON 형식 변경 시 하위호환(과거 데이터 소급 변경 금지)
	- 품질모니터링은 다른 레포(2슬롯) — 수정하면 그 레포 버전 규칙·배포 절차를 따른다
	- 4슬롯 결과 JSON에는 `pass_fail`·`stage`·`slot` 필드가 있으나 2슬롯 결과에는 `pass_fail`이 없다

## 주요 사용자 시나리오
사용자 또는 운영자가 실제로 어떤 상황에서 이 변경을 필요로 하는지 대표 시나리오를 적는다.

- 제조팀이 4슬롯으로 하루 생산 후 품질모니터링에서 **일별 수율**을 본다 — FAIL/재완성 JSON이 섞이면 수율이 틀리게 나온다
- 응용기술팀이 특정 시리얼의 불량 이력을 추적한다 — X단계 FAIL → 재검 → 완성의 경로를 한 화면에서 보고 싶다

## 오픈 질문
답을 아직 모르는 항목을 적는다. 추정으로 덮지 말고 REQ 초안 작성 이전에 확인할 질문으로 남긴다.

- OQ-1: 양산 DB `ctsm.product`를 읽는 시스템·사람이 누구인가 (품질모니터링 외)
	- 상태: Deferred
	- 처리 방안: K1을 "업로드 안 함"으로 정해 이번 범위에서 DB 문서 구성이 바뀌지 않음. FAIL 업로드를 다시 검토하는 후속 Discovery에서 확인
	- 종료 조건: 후속 Discovery 생성 시 그쪽으로 이관
- OQ-2: 품질모니터링을 4슬롯 결과에 맞춰 고치는 것이 "4슬롯만 작업" 방침 안에서 허용되는가 (2슬롯 레포 수정)
	- 상태: Answered (2026-09-30) — 모니터는 고치지 않고 4슬롯 저장 경로를 바꾼다(K2 결정). 반영 위치: # 4, FR-2·FR-3
- OQ-3: FAIL 기록을 품질모니터링에서 불량 분석용으로 보여 줄 필요가 있는가 (이번 범위 / 후속)
	- 상태: Deferred
	- 처리 방안: 이번 범위 밖(Out of Scope). 필요해지면 후속 Discovery(FAIL 분석·별도 컬렉션)로
	- 종료 조건: 후속 Discovery 생성 시 이관

### 오픈 질문 처리 기준
- `Open`: 아직 답이 없고 다음 단계 진행에 영향이 있는 상태다. 문서에 유지한다.
- `Answered`: 답이 확정된 상태다. 관련 본문/요구사항에 반영한 뒤 오픈 질문 목록에서는 제거하거나 resolved 기록으로 이동한다.
- `Deferred`: 지금 단계에서 결정하지 않고 다음 단계 또는 후속 이슈로 넘기는 상태다. 넘길 대상과 이유를 반드시 적는다.
- `Dropped`: 더 이상 유효하지 않은 질문이다. 삭제 사유를 짧게 남기고 목록에서 제거한다.
- 처리 원칙 1: 질문만 남기지 말고 반드시 `상태`, `처리 방안`, `종료 조건`을 함께 적는다.
- 처리 원칙 2: 답이 나온 질문은 본문 반영 없이 단순 삭제하지 않는다. 반영 위치를 먼저 갱신한다.
- 처리 원칙 3: High 영향 질문은 `Deferred` 처리 후 처리 방안에 REQ 인계 추적 방식을 명시한다.
