# 3. 문제점의 요약
문제의 현재 상태, 기대 상태, 관련 이해관계자, 제약사항을 정리한다. Discovery의 핵심 맥락을 가장 먼저 이해할 수 있어야 한다.

- 현재 상태
	- 4슬롯은 2레인 밀어내기: 사이클 n에서 X 통과한 보드를 작업자가 같은 레인 Y 칸으로 옮겨 사이클 n+1에서 Y 검사
	- 시리얼은 **프로그램이 자동 증가로 발급**(`serial_auto_increment=true`)하고, 보드에 기록하는 것은 **Y 단계 #9 UID**뿐이다. X 단계에는 UID 기록도 Flash 저장도 없다 (2026-06 시간 단축 때 X의 #2 UID·#5 SAVE 제거)
	- 그래서 X~Y 사이 보드에는 식별 정보가 없다. Y 칸 시리얼은 그 레인 pending에서 자동으로 채워지고, 프로그램은 "레인 n Y 칸 보드 = 레인 n X 통과 보드"라고 가정한다
	- 소프트웨어로 이미 막은 것: 시리얼 직접 입력에 의한 레인 교차·같은 보드 재투입(pending 무효), X 기록 없는 Y 투입(Y 차단). SIL B01·T4-5·T4-7로 확인
	- 막지 못하는 것: **보드만 바꿔 꽂는 경우**
		- 예) 레인1 X PASS 보드 A, 레인2 X FAIL 보드 B → 작업자가 B를 Y1에 꽂음 → Y1 시리얼 = A(자동) → B가 Y 항목을 통과하면 **X FAIL 보드 B가 A 시리얼로 완성·출하**
		- 레인 간 맞바꿈(A↔C, 둘 다 X PASS)은 불량 출하는 아니나 X 측정 데이터가 다른 보드에 붙는 추적성 오류
- 기대 상태
	- Y 칸에 꽂힌 보드가 그 레인 pending의 X 통과 보드가 아니면 Y 검사를 진행하지 않고 FAIL(쓰기 항목 #9 UID 이전에 차단)
	- X FAIL 보드는 Y에서 절대 완성되지 않는다
- 이해관계자
	- 응용기술팀(강병택) — 검사 프로그램·워크스페이스
	- 개발팀(펌웨어) — UID 명령 동작(Get UID 485 형식, SAVE 영향) 확인
	- 제조팀(캔탑스엠) — 검사 시간(택트) 증가 수용, 작업자 운영 규칙
- 제약사항
	- 공용 라이브러리 수정 금지, 2슬롯 경로 무변경
	- Flash 쓰기 횟수 증가(보드당 1회 → 2회)
	- 485(VL20) 통신사양서 R3에는 UID 절이 없다 — 485 Get UID 형식은 펌웨어 확인 필요

## 주요 사용자 시나리오
사용자 또는 운영자가 실제로 어떤 상황에서 이 변경을 필요로 하는지 대표 시나리오를 적는다.

- 작업자가 X FAIL 보드를 불량함에 넣지 않고 옆 레인 Y 칸에 꽂는다 (교대 직후·바쁜 시간)
- 작업자가 레인1·레인2 X 통과 보드를 서로 바꿔 Y 칸에 꽂는다
- STOP·재시작 후 작업자가 어느 보드가 어느 레인이었는지 헷갈린다

	- 상태: Open

### 오픈 질문 처리 기준
- `Open`: 아직 답이 없고 다음 단계 진행에 영향이 있는 상태다. 문서에 유지한다.
- `Answered`: 답이 확정된 상태다. 관련 본문/요구사항에 반영한 뒤 오픈 질문 목록에서는 제거하거나 resolved 기록으로 이동한다.
- `Deferred`: 지금 단계에서 결정하지 않고 다음 단계 또는 후속 이슈로 넘기는 상태다. 넘길 대상과 이유를 반드시 적는다.
- `Dropped`: 더 이상 유효하지 않은 질문이다. 삭제 사유를 짧게 남기고 목록에서 제거한다.
