## 0. 기본 원칙 (실무 컨센서스)

여러 검토(다른 AI/문헌 자료) 결과 수렴된 원칙:

> **"문제 발생 후 다시 테스트 = 비효율적.
>  처음 검사할 때 원인 추정용 지표를 같이 저장 = 효율적."**

**핵심 결론:**
- PASS/FAIL 단순 저장만으로는 **원인 분리 불가**
- 검사 시점에 **요약 통계(median, std, peak-to-peak, norm 등)** 함께 기록 필수
- 원시 100샘플 전체 저장 X → **이상품/재검품/골든샘플만** 선택 저장
- 이중 구조: **전수 요약값 + 이상 시 원시 로그**

---

## 1. 배경

양산 이관 후 품질 관리 필요. 현재는 수동으로 Result JSON 하나씩 열어보거나 MongoDB 접속해서 확인.

→ **이미 존재하는 Result JSON을 활용하되, 통계 지표를 추가하여 자동 집계/시각화 + 원인 추정 대시보드 구축**.

## 2. 측정 특성 분석 (검사 종류별)

| 검사 항목 | 동특성 | 권장 판정 방식 |
|---------|------|------|
| 24V/3.3V 전압 | 정적 DC | median + std |
| 전류 | 정적 DC | median + std |
| TILT (각도) | 정적 (모션지그 고정) | **median + std + peak-to-peak** |
| VIBE (1G 검증) | 정적 (중력 방향) | **median + cross-axis + vector norm** |

→ 모두 **정적(Static) 캘리브레이션** 성격. RMS 동특성 분석 아님.

## 4. 구현 단계

### 단계 0 — ff_vibetilt에 요약 통계 계산 추가 ⭐ (선행 필수)

**목표:** Result JSON에 통계 지표 함께 저장. 이후 모든 모니터링의 데이터 기반.

**대상 검사:**
- TILT_X/Y_232/485 (각도 검사 4종)
- VIBE_232/485 (진동 검사 2종)
- DPM_24V/3V3/CURR (전압/전류 검사 3종)

**계산 지표:**
| 검사 종류 | 계산할 통계 |
|---------|---------|
| TILT | median, trimmed mean, std, peak-to-peak |
| VIBE | median(target axis), cross-axis (non-target), vector norm |
| DPM | median, std (DC 안정도) |

**판정 로직 변경 (PASS / RETEST / FAIL 3단계):**
```
스펙 = [LSL, USL]
합격구간 = [LSL + GB, USL - GB]   // GB = guard band

PASS   : median ∈ 합격구간 && std ≤ σ_limit && pp ≤ pp_limit
RETEST : median ∈ 스펙 && (합격구간 밖 또는 안정도 borderline)
FAIL   : median ∉ 스펙 || retry 후에도 unstable
```

**Guard Band 초기 값:**
- 20° 항목 (스펙 ±0.2): GB = 0.03°
- 45° 항목 (스펙 ±0.5): GB = 0.07°
- 1G 항목 (스펙 ±0.01): GB = 0.002 g

**Stability 임계값:**
- TILT 20°: σ < 0.02°, pp < 0.08°
- TILT 45°: σ < 0.05°, pp < 0.15°
- VIBE: σ < 0.005~0.01 g, cross-axis ≤ 0.03 g, norm 0.98~1.02

**시간:** 4~8시간 (코드 수정 + 빌드 + 검증)
**파일:** `ff_vibetilt/VibeTilt.cs` (TILT_Internal, VIBE_Internal, VER_Internal에 통계 계산 추가)

### 단계 1 — MVP 모니터링 (Python, JSON 직접 스캔)

**목표:** 단계 0의 보강된 Result JSON으로 일별 집계.

**기능:**
1. Result 폴더 트리 재귀 스캔
2. JSON 파싱 → 집계
3. 콘솔 + HTML 리포트 출력

**집계 지표:**
- 총 검사 수, PASS/RETEST/FAIL, 불량률
- 검사 항목별 FAIL 카운트 + 원인 (스펙 out vs unstable vs cross-axis)
- 측정값 분포 (median, std, p-p)
- 시간대별 추이

**출력 예시:**
```
=== 2026-04-23 VL20 보드검사 (RS-485)_MP ===
총 16 · PASS 13 · RETEST 2 · FAIL 1 · 불량률 6.3%

검사 항목별:
  전류: FAIL 1 (median 3.72mA < 합격 4.07~6.93)
  TILT_Y +20°: RETEST 2 (σ 0.03° borderline)

측정값 분포:
  24V: median 23.61 ± 0.01 V (정상)
  TILT_Y -45°: median -45.05° ± 0.04° (정상, drift 모니터링)
```

**시간:** 2~4시간

---

### 단계 2 — SPC 관리도 추가 (드리프트 조기 감지)

**목표:** 합격품도 시계열로 보면 드리프트 보임 → 조기 경보.

**기능:**
- 검사 항목별 X-bar R 차트 (median 시계열)
- 관리한계 = 과거 PASS 평균 ± 3σ (스펙한계와 다름)
- Cpk 계산 (일/주 단위)
- Western Electric Rules 알람:
  - 1점이 ±3σ 밖 → 즉시 알람
  - 연속 7점 한쪽 → 드리프트
  - 연속 2점 ±2σ 밖 → 주의

**중요:** 스펙한계 (FAIL 기준) ≠ 관리한계 (정상 변동 범위). 관리한계 넘으면 "평소와 다름" 신호이지만 아직 FAIL 아님 → 조기 경보.

**시간:** 4~8시간

---

### 단계 3 — 이상품 원시 로그 자동 저장

**목표:** 원인 분리용 raw 데이터 확보 (전수 X, 이상 시만).

**저장 조건:**
- FAIL 발생 시
- RETEST 발생 시
- σ가 평소보다 2배 이상 클 때
- 통신 retry 발생 시

**저장 내용:**
- 최근 1~3초 원시 샘플
- 통신 프레임 로그 (parse error, timeout 등)

**파일:** `output/.../Result/{프로젝트}/{날짜}/{시리얼}.raw.json` (이상품만)

**시간:** 2~4시간 (ff_vibetilt에 raw buffer 보관 + 조건부 저장)

## 5. 운영 모델 (3 레이어)

| 레이어 | 무엇 | 언제 | 데이터 |
|------|------|------|------|
| **Layer 1** | 실시간 inline 판정 | 검사 중 | 샘플 → median/std → 즉시 PASS/RETEST/FAIL |
| **Layer 2** | 로트/시프트 SPC 감시 | 일/주 단위 | 요약 통계 시계열 → 관리도, Cpk |
| **Layer 3** | 사후 원시 로그 분석 | 이상 시만 | 이상품 raw 샘플 → 원인 분리 |

**핵심:** Layer 1+2로 90% 이상 잡고, Layer 3는 최후수단.

## 6. Check Standard (골든 샘플) 운영

**개념:** 같은 골든 샘플을 주기적으로 측정 → 측정 시스템 자체의 드리프트 감지

**주기:**
- 설비 시작 시 1회
- 교대마다 1회
- 알람 발생 시 1회
- 수리 후 1회

**판정:** 골든 샘플 측정값이 historical 평균에서 벗어나면 → 측정계/지그 점검 신호 (제품 불량 아님)

---

## 7. 알람 규칙 (예시 10개)

1. 단일 검사 FAIL → 즉시 운영자 알림
2. 같은 항목 연속 3회 FAIL → 라인 정지 권고
3. 1시간 내 FAIL 5건 이상 → 라인 정지
4. 불량률 일별 10% 초과 → 매니저 통보
5. 측정값이 관리한계 (±3σ) 밖 → 조사 필요
6. 연속 7점 평균이 한쪽으로 → 드리프트 알람
7. σ가 평소 2배 이상 → 노이즈 증가 (지그/배선 의심)
8. 통신 retry 률 평소 2배 → UART/485 충돌 의심
9. Cpk < 1.33 (일일) → 공정능력 부족 경고
10. 골든 샘플 측정값 드리프트 → 측정 시스템 점검

## 11. 리스크 / 주의

- **단계 0 적용 시 검사 시간 증가** — median/std 계산은 ms 단위라 거의 영향 없을 것
- **Result JSON 크기 증가** — stats 필드 추가로 한 검사당 +200B 정도
- **운영자 교육** — RETEST 개념 설명 필요 (FAIL과 다름)
- **Guard Band 튜닝** — 초기 값 후 양산 데이터로 1~2개월 조정
