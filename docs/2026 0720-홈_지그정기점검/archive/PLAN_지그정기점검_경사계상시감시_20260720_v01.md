## 1. 배경 — 왜 지금 가능해졌나

`setzcur` 제거(R1b1) 전에는 이 감시가 **원리적으로 불가능**했다.

```
[제거 전]  매 사이클 setzcur → 경사계 0점 Z := 현재 자세 M
           → 다음 사이클 판독은 항상 0 근처
           → 기구가 얼마나 틀어졌든 화면상 0.00x  (틀어짐이 0점에 흡수됨)

[제거 후]  경사계 0점 Z = 공장(중력) 기준에 영구 고정
           → 영점 초기화 시 판독 = 기구 자세 M의 절대 수평 오차 (≈ D)
           → 홈센서 마모 / 지그 재조립 / 센서 재장착이 숫자로 보인다
```

`REF_경사계_tau실측결과` §8 마지막 줄이 남긴 숙제가 정확히 이것이다:

> **`D`의 시간 이동** — 홈센서 마모·지그 재조립·센서 재장착 시 **조용히 변한다.** 이번 측정은 1시점 스냅샷

τ = +0.0903°는 2026-07-16 **한 시점**의 값일 뿐이고, 이게 시간에 따라 어디로 가는지 볼 수단이 없다.
setzcur를 제거한 지금이 그 계기판을 다는 시점이다.

### 사양 근거 (2026-07-20 확정)

지그요청서 작성 개발자에게 직접 문의한 결과 **원 의도에 레퍼런스 영점(setzcur)은 없었다.**
→ setzcur 제거는 개선이 아니라 **사양 복귀**다. 동시에 "요청서에 없으니 감시 요구도 없다"는 뜻이므로,
본 기능은 **양산 판정에 개입하지 않는 부가 감시**로 설계한다 (§5).

`REF_경사계_tau실측결과` §9 담당자 확인 항목 중 "setzcur가 의도에 포함됐나" → **해소(아니오).**
남은 확인 항목: `상용센서 기준 0 : -0.05 ~ 0.05`의 ±0.05가 지그 위치 허용오차(A)인지 DUT 출력 spec(B)인지.

## 2. 무엇을 재나

`MotionJig.InitMotionZero`의 흐름과 측정점:

```
 3. setdir5/6 (부호 설정)                        MotionJig.cs:844
 4. MoveSteps(stepsToZero)  홈 + 1250스텝        MotionJig.cs:852
    Thread.Sleep(_zeroSettleWait)                MotionJig.cs:858
    ────────────────────────────────────────────────────────────
 ★  여기서 경사계 판독  r_pre                     ← 신규 측정점
    = 기구가 만든 "0도 자세" M 의 절대 수평 오차
    ────────────────────────────────────────────────────────────
 5. FineAdjust(target=0, strict 0.03)            MotionJig.cs:864
    → 수렴 잔차 ρ, 이동 step 수 n_step
 6. (gyro_setzcur=false → 미실행)                MotionJig.cs:876
```

| 지표 | 의미 | 감시 대상 |
|---|---|---|
| **r_pre** | 홈센서+고정스텝이 도달한 물리 자세의 수평 오차 | **주** — 기구/홈센서/장착 틀어짐 |
| n_step | FineAdjust가 보정한 스텝 수 (= r_pre / 0.1125 반올림) | 보조 — r_pre와 중복이나 이산값이라 추세가 선명 |
| ρ | 수렴 잔차 | 보조 — 이미 로그에 있음 (수렴 품질) |

r_pre가 주 지표다. n_step·ρ는 파생값이므로 **r_pre만 확실히 남기면 나머지는 사후 계산 가능**하다.

### 이미 읽고 있다 — 로깅만 안 될 뿐

`FineAdjust`는 진입 직후 `GyroGetAngle`로 이미 이 값을 읽는다 (`MotionJig.cs:1509`).
즉 **UART 왕복을 추가할 필요가 없다.** 사이클 타임 영향 0.

## 3. 핵심 문제 — MP에서 로그가 안 남는다

오늘(7/20) 10층 실기 검증이 MP 워크스페이스라 필요한 로그가 빠진 것의 구조적 원인:

| 위치 | 로그 | IsTest 게이트 | MP에서 |
|---|---|---|---|
| `MotionJig.cs:1515` | `[FINE] 시작: target=, current=, 오차=` | **있음** | ❌ 안 남음 |
| `MotionJig.cs:1575` | `[FINE] step N: moved=, current=, 오차=` | **있음** | ❌ 안 남음 |
| `MotionJig.cs:1533` | `[FINE] 수렴 완료: actual=, 오차=` | 없음 | ✅ 남음 |
| `MotionJig.cs:1594` | `[FINE] maxSteps 초과` | 없음 | ✅ 남음 |

`current`(= r_pre)는 **TEST에서만** 나온다. 정기점검은 **양산 라인이 매일 돌 때** 데이터가 쌓여야
의미가 있으므로, 이 값은 IsTest 게이트 밖으로 나와야 한다.

단, `[FINE] step N` 스텝별 로그는 양산에서 노이즈다 — **게이트 유지.**
새로 빼는 건 **사이클당 1줄**뿐이다.

## 4. [선행 적용] setzcur 유무를 MP 로그에서 판별 가능하게

> **본 절은 정기점검(§5)과 독립적으로, 먼저 적용할 것을 권한다.**
> 정기점검 데이터의 유효성이 이 절에 의존한다.

### 4.1 문제 — 미실행과 실행성공이 똑같이 침묵한다

`MotionJig.cs:876`은 `if (GetParamBool(param, "gyro_setzcur", false))` 로 블록을 통째로 건너뛴다.
그 결과 **미실행과 실행성공이 로그상 동일하게 침묵**한다.

| 상황 | MP 로그 |
|---|---|
| 미실행 (R1b1 기본) | **없음** |
| 실행 성공 | **없음** (`[GYRO] RX:` 는 IsTest 게이트, `MotionJig.cs:2026`) |
| 실행 실패 | `[ZERO] FAIL: setzcur 실패` |

**로그만 봐서는 "제거된 장비"와 "제거 전 장비"를 구분할 수 없다.**
`MODULE_VERSION="R1b1"`은 `GetInfo`의 `ver`(`MotionJig.cs:73`)로만 나가고, **JSON으로 `gyro_setzcur: true`를
복원하면 버전으로도 구분 불가**하다. 버전이 아니라 **실효 상태**를 찍어야 한다.

r_pre를 몇 주 쌓아놓고 나중에 *"이 구간은 setzcur가 살아있던 데이터 아닌가?"* 를 판별할 근거가
없으면 수집 데이터 전체가 흔들린다. 오늘(7/20) *"공장초기화 전후 비교를 0.7.9로 돌려 무효"* 와
같은 계열의 문제다 — **로그가 자기 조건을 증명하지 못하는 것.**

### 4.2 수정 — 양쪽 분기 모두 로그를 남긴다

`MotionJig.cs:876`:

```csharp
if (GetParamBool(param, "gyro_setzcur", false))
{
    if (!GyroSetZero(gyro, log))
    {
        log("[ZERO] FAIL: setzcur 실패");          // 기존 유지
        LogErrorInfo("GYRO_SETZCUR", log);
        return false;
    }
    log("[ZERO] setzcur 실행함 (gyro_setzcur=true)");        // 신규
}
else
{
    log("[ZERO] setzcur 실행안함 (gyro_setzcur=false, 경사계 공장영점 기준)");  // 신규
}
```

- `IsTest` 게이트 **밖** → MP/TEST 공통. 사이클당 1줄, 기존 `[ZERO]` 태그·스타일 유지
- **어느 경로로도 반드시 한 줄이 남는다** — 침묵하는 경우가 없어짐

### 4.3 판별 문자열 — Contains 기반

프로젝트 규칙(판정은 계산이 아닌 로그 문자열 Contains)에 맞춰, **서로의 부분문자열이 되지 않게** 잡았다.

| 판별 대상 | Contains 문자열 |
|---|---|
| 제거 적용된 로그 (R1b1 기본) | `setzcur 실행안함` |
| setzcur 살아있는 로그 | `setzcur 실행함` |
| 구버전(R0 이하) 로그 | **둘 다 없음** → 이 자체가 구버전 식별자 |

> `실행함` / `실행안함` 은 한쪽이 다른 쪽의 부분문자열이 **아니다**
> (`실행안함`에 `실행함`이 들어있지 않음 — 사이에 `안`이 있다). 순서 무관하게 안전하다.
> `실행` / `미실행` 조합은 `미실행`이 `실행`을 포함하므로 **피했다.**

이 세 갈래로 **로그 파일 하나만 보면 어느 조건에서 나온 데이터인지 자기증명**이 된다.
품질모니터링에서 일자별 구간 분리에 그대로 쓸 수 있다.

### 4.4 결과 details에도 기록 (권장)

로그는 사람이 읽고 details는 기계가 읽는다. 추세 분석은 후자를 쓰므로 양쪽에 남긴다.

```
"gyro_setzcur": false          ← 실효값 (JSON 설정값 그대로)
```

`_comment` 규칙에 따라 JSON 쪽에는 이미 주석이 붙어 있으므로(§5.2), details는 값만 기록한다.

### 4.5 적용 범위

- 대상: `MotionJig.cs` 단일 파일, `InitMotionZero` 1곳
- **JSON 변경 없음** (`gyro_setzcur`는 R1b1에서 이미 추가됨)
- 빌드 산출물 외 영향 없음 → **단독 커밋 가능**

## 6. 스펙 · 알림 · 점검 작업

### 6.1 3단계 판정

| 구간 | 로그 | 작업자 알림 | PASS/FAIL |
|---|---|---|---|
| \|r_pre\| ≤ warn (0.15) | `OK` | 없음 | 영향 없음 |
| warn < \|r_pre\| ≤ ng (0.30) | `WARN` | **없음** (로그·details만) | 영향 없음 |
| \|r_pre\| > ng (0.30) **연속 3회** | `NG` | **팝업 → 점검 유도** | 영향 없음 (기본) |

### 6.2 알림 정책 — 매 사이클 띄우면 안 된다

양산 라인에서 사이클마다 팝업이 뜨면 작업자가 조건반사로 확인을 눌러 **기능이 무력화**된다.
알림에 두 겹의 억제를 건다.

**(1) 연속 N회 이탈에서만** (`jig_health_ng_streak`, 기본 3)

1회 튐은 감시 대상이 아니다 — 작업자 접촉, 설비 진동, 인접 공정 충격으로 얼마든지 난다.
**기구가 실제로 틀어졌다면 그 상태가 유지되므로 연속으로 걸린다.** 연속 카운터는
OK/WARN이 한 번 나오면 리셋한다.

**(2) 교대당 1회만** (`jig_health_prompt_once_per_shift`, 기본 true)

한 번 알리고 작업자가 점검했으면 그 교대 동안 다시 묻지 않는다.
실제로 기구가 틀어진 상태면 점검 전까지 계속 NG가 나오는데, 그때마다 팝업이 뜨면 라인이 못 돈다.
로그·details에는 계속 `NG`가 남으므로 **기록은 유실되지 않는다.**

> 교대 경계 판정 기준은 미확정(§9-8). 프로그램 재시작 기준으로 갈지, 날짜 변경 기준으로 갈지
> 현장 교대 운영에 맞춰야 한다. 가장 단순한 건 **프로그램 실행 단위(정적 플래그 1개)** 다.

### 6.3 알림 = 점검 작업 지시서

기존 작업자 확인 메커니즘을 그대로 쓴다 — **신규 UI 없음.**

- `libraries["confirmCallback"]` (`Func<string, bool>`) — `MotionJig.cs:666`, `VibeTilt.cs:3238`에서 이미 사용 중
- 호출부(`MotionJig.cs:677` 부근)가 이 콜백을 갖고 있으므로 §5.1(b)대로 판정을 호출부에 두면 그대로 호출 가능

팝업 문구는 JSON `jig_health_prompt`로 빼서 **현장에서 점검 절차를 고칠 수 있게** 한다
(하드코딩 금지 규칙과도 맞음). `{dev}` / `{ng}`는 실측값으로 치환.

```
지그 수평이 기준을 벗어났습니다.

측정: 0.341도 (기준 0.30도)

[점검 절차]
1. 지그 고정 볼트 풀림 확인
2. 홈센서 위치/오염 확인
3. 경사계 장착 상태 확인

점검 후 확인을 누르세요. 취소 시 검사가 중단됩니다.
```

| 작업자 선택 | 동작 | 기록 |
|---|---|---|
| 확인 | 검사 계속 진행 | `[JIG] 작업자 점검 확인` + `jig_check_prompted: true` |
| 취소 | 해당 항목 FAIL, 검사 중단 | `[JIG] 작업자 취소 — 지그 점검 필요` |

**팝업 확인 자체가 "점검했다"는 기록**이 된다. 별도 점검 이력 시스템이 필요 없다 —
로그와 details에 언제 알림이 떴고 언제 확인됐는지가 남는다.

### 6.4 양산 판정에는 개입하지 않는다 (초기 정책)

`jig_health_fail_on_ng`는 **기본 false**다. NG여도 제품은 계속 흐른다.

**이유:** 요청서에 없는 자체 감시이고, 임계가 아직 실측 근거 없는 초안이다.
초기부터 라인을 세우면 **오탐 1회로 기능 전체가 꺼진다**(현장에서 JSON을 false로 바꿔버림).
데이터로 임계를 확정한 뒤(§6.5) FAIL 승격을 판단한다.

> 다만 작업자가 팝업에서 **취소**를 누르면 그건 사람의 판단이므로 FAIL·중단이 맞다.
> 자동 판정과 사람 판정을 구분한다.

### 6.5 스펙 확정 절차 — 임계는 지금 정할 수 없다

현재 0.15 / 0.30은 **공학적 초안**이지 스펙이 아니다.

```
1 스텝 = 0.1125°
2026-07-16 실측 τ = +0.0903     (기구가 이미 0.8스텝 틀어져 있던 상태, n=1)

경고 0.15 = 1.3스텝  — 현재값 대비 1.7배. 평상시엔 안 울려야 한다
NG   0.30 = 2.7스텝  — FineAdjust가 3스텝 보정 = 명백한 기구 이동
```

**표본이 1개다.** 재현성도, 일간 변동폭도, 축별 차이도 모른다. 확정 절차:

| 단계 | 내용 | 판단 |
|---|---|---|
| 1 | `jig_health_check: true`, 알림 **off**(`ng_streak`를 크게)로 배포 | 데이터만 수집 |
| 2 | 1~2주 / 최소 200사이클, X·Y 각각 | 분포 확보 |
| 3 | 평상시 분포 확인 — 중심값 μ₀, 산포 σ | 일간 변동이 있나 |
| 4 | `warn = μ₀ ± 3σ` 또는 **1스텝(0.1125°)** 중 큰 값 | 오탐 없는 하한 |
| 5 | `ng` = 검사 spec 역산 — 기울기 spec ±0.2° 대비 유의미한 잠식점 | 공학적 상한 |
| 6 | v02로 개정 후 알림 on | 스펙 확정 |

**4·5의 두 근거가 충돌하면 5(제품 영향)를 우선**한다. 감시의 목적은 통계가 아니라 출하 품질이다.

> 참고: FineAdjust는 250스텝(≈28°)까지 보정하고 30°에서 발산 가드가 걸리므로(`MotionJig.cs:1579`),
> **0.3°는 FineAdjust에게는 전혀 문제없는 값**이다. 검사는 정상 완주한다.
> 그래서 기존 검사망이 이걸 못 본다 — 그게 이 기능의 존재 이유다.
