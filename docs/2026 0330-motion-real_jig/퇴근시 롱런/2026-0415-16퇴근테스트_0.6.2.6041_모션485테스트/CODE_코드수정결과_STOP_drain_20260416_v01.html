2. 원인 분석

근본 원인: STOP 5x 응답 미소비

VL20 개발팀 유의사항: "STOP,1 명령을 약 10ms 주기로 여러 번 송신하여 [STOP,0,1] 응답의 ret(0)을 파싱합니다. 충돌로 인하여 응답이 없는 경우가 있습니다."

현재 구현: STOP 5회 송신은 유의사항대로 구현했으나, 응답을 읽지 않고 다음 명령으로 진행하고 있었음.

문제 흐름

PC TX:   <STOP,1> ─10ms─ <STOP,1> ─10ms─ <STOP,1> ─10ms─ <STOP,1> ─10ms─ <STOP,1>
                   (응답 안 봄)   (응답 안 봄)   (응답 안 봄)   (응답 안 봄)

버퍼에 쌓임: [GAC잔류...][STOP,0,1][STOP,2,1][STOP,2,1][STOP,2,1][STOP,2,1]
                                                    ↑ 이 응답들이 다음 검사에 혼입

변경 2: VlDrain 메서드 신규 신규

private static void VlDrain(IComm vl, Action<string> log, int timeoutMs = 200)
{
    var deadline = DateTime.UtcNow.AddMilliseconds(timeoutMs);
    int emptyCount = 0;
    while (emptyCount < 3 && DateTime.UtcNow < deadline)
    {
        var resp = vl.Recv(timeout: 50, recv_mode: "line");
        if (empty)
            emptyCount++;       // 빈 응답 카운트
        else
            emptyCount = 0;     // 데이터 있으면 리셋
    }
    // 연속 3회 빈 응답 (150ms) 또는 200ms 타임아웃 → 버퍼 비었다고 판단
}

4. 영향 분석

시간 영향

  • STOP당 ~150-200ms 추가 (VlDrain)
  • 라운드당 STOP 2~3회 → ~0.5초/라운드 증가
  • 300회 기준 ~2.5분 증가 (무시 가능)

양산 영향

  • 양산은 매 보드 전원 OFF/ON → UART hang 누적 불가
  • 1회 내 오불량 확률 극히 낮음 (81회 연속 정상 실적)
  • 양산 리스크 없음
  • 제품 메모리/캘리브레이션 영향 없음 (UART 레벨 문제)
변경하지 않은 것:
  • STOP 5x @ 10ms 패턴 — VL20 개발팀 권장 유지
  • RS-232 STOP 흐름 — 단일 STOP이라 충돌 없음
  • Framework / Architecture — 절대 규칙 준수
