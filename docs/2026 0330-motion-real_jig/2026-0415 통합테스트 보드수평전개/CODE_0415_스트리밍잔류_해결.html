스트리밍 잔류 문제 원인 및 해결

날짜: 2026-04-15 | 버전: v0.6.2.60415 | 커밋: f5fcc4c

문제 요약

보드 검사(485)에서 VIBE→TILT 전환 시, 또는 이전 세션의 스트리밍이 남아있을 때 COMM/TILT FAIL 발생.

근본 원인: FW 스트리밍(GAC/AN) 데이터가 STOP 후에도 잔류하여, 후속 명령(MODE, VER)의 응답을 오염시킴.

발생 시점현상빈도
VIBE → TILT 전환GAC 잔류 → MODE,6 실패 → AN 대신 GAC 수신 → TILT FAIL간헐 (타이밍 의존)
이전 세션 잔류AN 스트리밍 잔류 → COMM의 VER 응답 오염 → COMM FAIL이전 테스트가 비정상 종료 시
연속 테스트 2회차STOP RV=1 (이미 정지) → VER_Internal이 에러 처리 → COMM FAIL매번 (정상 상태에서도)

문제 1: VIBE→TILT 전환 시 GAC 잔류

증상

TX: <MODE,1,6>
RX: ...GAC...[MODE,1,1,02]...GAC...   ← MODE 변경 실패! RV=1, 여전히 MODE 02
TX: <START,1>
RX: ...GAC...GAC...[START,2,1]...GAC   ← START도 실패, GAC 계속 수신
→ [TILT] 기울기 데이터 수집 실패 → FAIL

원인

VIBE finally 블록에서 STOP + 버퍼 클리어 + MODE,0을 했지만, GAC 스트리밍이 완전히 배출되기 전에 TILT가 시작됨. TILT의 STOP → MODE,6 사이에 MODE,0이 없어서 스트리밍 모드(02)가 유지됨.

수정 전/후

항목수정 전수정 후
TILT tests STOP → MODE,6 → START STOP → MODE,0 → sleep 200ms → MODE,6 → START
JSON 수정 (TILT_X, TILT_Y): 
"tests": [
  {"_comment": "스트리밍 잔류 방지: STOP → MODE,0 → sleep 후 MODE,6"},
  {"command": "<STOP,1>"},         // 활성 스트리밍 정지
  {"command": "<MODE,1,0>"},       // MODE 0으로 초기화
  {"sleep": 200},                     // 버퍼 배출 대기
  {"command": "<MODE,1,6>", "expected_response": "[MODE,0,1,06]"},
  {"command": "<START,1>"},
  {"command": "<STOP,1>"},
  {"command": "<MODE,1,0>"}
]

문제 2: 이전 세션 스트리밍 잔류 → COMM FAIL

증상

TX: <MODE,1,0>
RX: [AN,1,-0.77,0.60][AN,1,-0.77,0.60]...   ← 이전 세션의 TILT AN 잔류
    [VER] MODE RV 오류: 1 (패킷 수신 불가 상태)
TX: <VER,1>
RX: ...AN...[VER,0,1,F/W ver.2.0.2]...AN...  ← VER 응답이 AN에 묻힘
    [VER] 응답 명령 불일치: [AN,1,-0.77,0.60] → FAIL

원인

이전 테스트가 비정상 종료(FAIL, 취소 등)되면 보드가 스트리밍 상태로 남음. 다음 세션의 COMM이 MODE,0만 보내면, 활성 스트리밍 중에는 MODE 변경이 안 됨 (STOP을 먼저 해야 함).

항목수정 전수정 후

COMM tests (232 MP) VER (보호 없음) STOP → MODE,0 → sleep 200 → VER

문제 3: STOP RV=1 → COMM FAIL (이미 정지 상태)

증상

TX: <STOP,1>
RX: [STOP,1,1]                        ← RV=1: 이미 정지 상태
    [VER] STOP RV 오류: 1 (패킷 수신 불가 상태) → FAIL
TX: <VER,1>
RX: [VER,0,1,F/W ver.2.0.2]          ← VER은 정상인데 이미 FAIL 처리됨

원인

COMM tests에 STOP을 추가했지만, 보드가 이미 정지 상태면 [STOP,1,1] (RV=1)을 반환. VER_Internal이 모든 RV!=0을 에러로 처리하여 FAIL 발생.

STOP의 RV=1은 "이미 정지" 상태로 정상임. 에러가 아님.

코드 수정

VibeTilt.cs — VER_Internal: 
// 수정 전
if (!TryGetRvCode(mergedLast, out int rv) || rv != 0)
{
    logAction($"[VER] {commandToken} RV 오류: {rv} ({GetRvDescription(rv)})");
    ok = false;
    stepOk = false;
}

// 수정 후
if (!TryGetRvCode(mergedLast, out int rv) || rv != 0)
{
    bool isStopRv1 = commandToken.StartsWith("STOP") && rv == 1;
    if (isStopRv1)
    {
        logAction($"[VER] {commandToken} RV=1 (이미 정지 상태, 무시)");
        // ok, stepOk 변경 안 함 → PASS 유지
    }
    else
    {
        logAction($"[VER] {commandToken} RV 오류: {rv} ({GetRvDescription(rv)})");
        ok = false;
        stepOk = false;
    }
}

핵심 원칙: 스트리밍 모드 전환 전에는 반드시 STOP → MODE,0 → sleep 3단계를 거친다.
STOP만으로는 부족 (버퍼 잔류), MODE,0만으로는 부족 (활성 스트리밍 중 MODE 변경 불가).
